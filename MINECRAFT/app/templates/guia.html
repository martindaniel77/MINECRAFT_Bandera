1. Lingote de Hierro

Esteganografía en metadatos, Base64 y cifrado César
{% if 'iron' in inv %}✓ Resuelta{% endif %}
Dificultad: Fácil Overworld Prerrequisito: ninguno Familia: cripto / forense

Objetivo de aprendizaje: distinguir codificación de cifrado, extraer metadatos de un PNG y revertir dos capas (Base64 + ROT-13) sin conocer la bandera de antemano.

¿Qué es?

La esteganografía oculta la existencia misma de un mensaje dentro de otro archivo; la criptografía oculta su significado. En los PNG existen bloques de texto (tEXt, iTXt, zTXt) pensados para guardar autor, descripción o comentario. Son invisibles al abrir la imagen, pero cualquier herramienta de metadatos los lee.

Base64 no cifra: es una codificación de transporte que convierte bytes en 64 símbolos imprimibles (A–Z, a–z, 0–9, +, /, con = de relleno). Cualquiera puede decodificarla. El cifrado César desplaza cada letra un número fijo de posiciones; ROT-13 usa 13 y es involutivo (aplicarlo dos veces devuelve el original).

¿Cómo funciona?

El reto guarda el secreto en el campo de comentario de la imagen. El flujo mental es: ver el archivo → preguntar qué datos contiene → identificar una cadena rara → reconocer su formato → invertir las transformaciones en orden inverso. El orden importa: si primero se cifró y después se codificó, debes decodificar y luego descifrar.

¿Por qué importa?

Los metadatos filtran información sensible en la vida real: autor, software usado, rutas locales e incluso coordenadas GPS de fotografías. Un atacante que solo mira "el contenido visible" se pierde una capa entera de información. Por eso el reconocimiento de archivos es una habilidad base en forense y en pentesting.

Profundización

Base64 incrementa el tamaño aproximadamente un 33 % porque representa 3 bytes con 4 caracteres. El sufijo = indica relleno. Una cadena que termina en = y solo usa ese alfabeto es una pista gráfica muy fuerte. ROT-13 se reconoce porque las letras tienen una distribución "desplazada" pero la estructura de palabras y símbolos se mantiene. También conviene saber que strings puede mostrar cadenas incrustadas aunque exiftool no interprete el campo.

Ejemplo de código vulnerable 
comment = png.get_text("Comment")
decoded = base64.b64decode(comment).decode("utf-8")
flag = codecs.decode(decoded, "rot_13")
print(flag)  # el secreto queda expuesto al que sepa leer metadatos
Herramientas y comandos de ejemplo (no son la solución) 
# 1. Inspeccionar metadatos y buscar campos de texto:
exiftool imagen.png
strings imagen.png | head -40

# 2. Decodificar la capa Base64:
echo "CADENA_BASE64" | base64 -d

# 3. Deshacer el desplazamiento César:
echo "CADENA_ROT13" | tr 'A-Za-z' 'N-ZA-Mn-za-m'

# 4. Confirmar el tipo real del archivo:
file imagen.png
Pista conceptual (ábrela solo si te atascas)

Hay dos capas y el orden importa. Prueba Base64 → ROT-13 y también ROT-13 → Base64; quédate con la salida que tenga sentido legible. No necesitas adivinar la bandera.

Cómo defenderse: elimina metadatos antes de publicar (exiftool -all= imagen.png) o vuelve a codificar la imagen. No incluyas rutas, nombres de usuario ni GPS. Trata los metadatos como datos no confiables y escanea archivos con DLP/AV.
Al terminar, comprueba que puedes:
  • Explicar por qué Base64 no es cifrado.
  • Describir qué hace tr 'A-Za-z' 'N-ZA-Mn-za-m'.
  • Nombrar dos metadatos que puedan filtrar información.
Curiosidad: el cifrado César debe su nombre a Julio César, que lo usaba para mensajes militares. ROT-13 es un caso particular y es su propio inverso. En casos reales, fotos con EXIF han revelado la ubicación exacta de quien las tomó.

2. Diamante en Y=-58

Inyección SQL (SQLi)
{% if 'diamond' in inv %}✓ Resuelta{% endif %}
Dificultad: Media Overworld Prerrequisito: tema 1 OWASP: A03 Injection

Objetivo de aprendizaje: reconocer cuándo una entrada del usuario se concatena en una consulta SQL y entender cómo cambiar la lógica de la consulta sin saber la sintaxis completa de la base de datos.

¿Qué es?

La inyección SQL ocurre cuando datos controlados por el usuario se insertan dentro de una sentencia SQL como si fueran código. La base de datos no distingue entre "texto que viene del formulario" y "instrucción escrita por el programador": ejecuta todo junto. Es el riesgo A03: Injection del OWASP Top 10.

¿Cómo funciona?

La aplicación construye la consulta con una cadena de texto. Una comilla simple ' cierra el literal que esperaba el programador; a partir de ahí, lo que escribas es sintaxis SQL real. OR 1=1 convierte la condición en verdadera para todas las filas y -- comenta el resto de la línea, eliminando filtros posteriores como AND is_locked = 0. En consultas LIKE '%...%' hay que cerrar también el comodín.

¿Por qué importa?

Permite leer registros ajenos, saltarse autenticación, modificar o borrar datos y, según los privilegios del usuario de la base de datos, llegar a ejecutar comandos en el servidor. Es una de las vulnerabilidades más antiguas y más rentables: lleva décadas apareciendo en informes de incidentes.

Profundización

No todas las SQLi son iguales. En error-based la aplicación devuelve el error de la BD; en UNION-based se añaden columnas a la consulta original (deben coincidir en número y tipo); en boolean-based blind se infiere información según cambie o no la respuesta; en time-based blind se usa una función de retardo para medir el tiempo de respuesta. El motor importa: MySQL acepta # como comentario, SQLite y PostgreSQL suelen necesitar -- con espacio final. Por eso copiar payloads sin entender el contexto falla tan a menudo.

Ejemplo de código vulnerable 
sql = f"SELECT * FROM cofres WHERE nombre LIKE '%{chest_query}%' AND is_locked = 0"
cursor.execute(sql)  # la entrada del usuario se concatenó al SQL
Ejemplos de SQLi para practicar (no son la solución) 
# Bypass de filtro / condición siempre verdadera:
' OR 1=1 --
' OR '1'='1
admin' --

# UNION-based (conceptual, ajusta el número de columnas):
' UNION SELECT NULL, NULL --

# Time-based (conceptual):
' OR SLEEP(5) --

# Herramientas: sqlmap (con petición guardada), Burp Suite, navegador, sqlite3.
sqlmap -r peticion.txt --dbs
Pista conceptual (ábrela solo si te atascas)

El buscador usa LIKE '%...%'. Piensa en cómo cerrar la comilla y el comodín a la vez, y en qué parte de la condición conviene neutralizar el filtro is_locked. Observa la respuesta: ¿cambia el número de resultados o solo el contenido?

Cómo defenderse: usa prepared statements / consultas parametrizadas (cursor.execute(sql, (valor,))) en lugar de concatenar. Valida y normaliza la entrada, aplica mínimo privilegio al usuario de la BD y mantén un WAF como capa adicional, nunca como única defensa.
Al terminar, comprueba que puedes:
  • Explicar qué hace cada carácter de ' OR 1=1 --.
  • Diferenciar SQLi UNION-based de time-based.
  • Escribir la versión segura de la consulta con parámetros.
Curiosidad: la primera SQLi documentada apareció en 1998 en la revista Phrack. Hoy sigue ocupando el puesto A03 del OWASP Top 10 y suele aparecer en aplicaciones internas "de confianza".

3. Portal al Nether

Enumeración de rutas y validación por allowlist
{% if 'portal' in inv %}✓ Resuelta{% endif %}
Dificultad: Fácil Overworld Prerrequisito: tema 1 OWASP: A01 / info disclosure

Objetivo de aprendizaje: entender la diferencia entre una shell real y una consola simulada, y por qué una lista blanca de comandos es más segura que intentar prohibir todos los comandos peligrosos.

¿Qué es?

La enumerateción es la fase de reconocimiento en la que descubres qué recursos existen: archivos, carpetas, comandos o servicios. Una allowlist (lista blanca) es un mecanismo de control que solo permite lo que está explícitamente autorizado y rechaza todo lo demás por defecto.

¿Cómo funciona?

Esta consola no es un intérprete de comandos del sistema: acepta un conjunto cerrado (ls, cat, help, clear) y resuelve las rutas contra un diccionario interno. Es decir, el "sistema de archivos" es un mapa en memoria. El reto consiste en enumerar ese mapa y leer el archivo que contiene la llave de ignición.

¿Por qué importa?

Si una aplicación expone rutas, nombres de archivo o estructuras de directorios, está regalando información útil a un atacante. Y si además construye rutas concatenando la entrada del usuario sin normalizar, aparece el path traversal: usar ../ para salir del directorio permitido. Aquí el diseño con diccionario evita ese problema, pero conviene saber cómo se produce para reconocerlo en otros sistemas.

Profundización

Una blocklist (lista negra) intenta prohibir rm, cat, ;, ../… y siempre se queda corta: basta un comando, un alias o una codificación que nadie prohibió. La allowlist invierte la carga de la prueba: si algo no está en la lista, no se ejecuta. Este es el principio default deny. En rutas, la versión segura es normalizar con os.path.realpath() y comprobar que el resultado sigue dentro del directorio base.

Ejemplo de código con allowlist 
ALLOWED = {"ls", "cat", "help", "clear"}

if command not in ALLOWED:
    return "Comando no permitido"

# Las rutas se resuelven contra un diccionario, no contra el disco real:
target = CAVE_ROUTES.get(argument)
if target is None:
    return "Ruta no encontrada"
Comandos de ejemplo (no son la solución) 
# Enumerar el contenido de la raíz:
ls

# Entrar en una ruta y volver a listar:
ls /cueva/<nombre>

# Leer un archivo concreto:
cat /cueva/<nombre>/<archivo>

# Ver los comandos aceptados:
help
clear
Pista conceptual (ábrela solo si te atascas)

Empieza con ls sin argumentos. La salida te da el nombre de la primera carpeta; repite el proceso dentro de ella. En algún nivel aparecerá un archivo de texto con el material para encender el portal.

Cómo defenderse: validar comandos por allowlist, normalizar y acotar rutas, no exponer el mapa completo de archivos, registrar intentos de acceso fallidos y ejecutar cualquier funcionalidad de shell con el mínimo privilegio posible.
Al terminar, comprueba que puedes:
  • Explicar por qué una allowlist supera a una blocklist.
  • Definir path traversal y describir cómo se evita.
  • Diferenciar una shell real de una consola simulada.
Curiosidad: los bad characters filters de los años 90 prohibían espacios y puntos y comilla, pero olvidaban tabuladores o saltos de línea. Es el origen de muchos bypasses clásicos: prohibir no es lo mismo que permitir solo lo seguro.

4. Lingote de Oro

Stored XSS y robo de cookies de sesión
{% if 'gold' in inv %}✓ Resuelta{% endif %}
Dificultad: Media Nether Prerrequisito: nociones de HTML OWASP: A03 XSS

Objetivo de aprendizaje: comprender por qué guardar y volver a mostrar texto sin escaparlo permite ejecutar JavaScript en el navegador de otra persona, y qué barreras (CSP, HttpOnly) limitan el daño.

¿Qué es?

Cross-Site Scripting (XSS) es una vulnerabilidad de inyección de código en el lado del cliente: la aplicación incluye datos del usuario en una página sin escaparlos y el navegador los interpreta como HTML o JavaScript. Hay tres variantes: reflejado (el payload va en la petición y vuelve en la respuesta), almacenado (se guarda en la base de datos y afecta a quien visite después) y DOM-based (el script modifica el DOM en el navegador).

¿Cómo funciona?

Aquí el ataque es almacenado: escribes una nota en el tablón de ofertas, el servidor la guarda sin sanitizar y la plantilla la renderiza con |safe, que desactiva el escapado automático. Cuando el Piglin Guard abre la página con su sesión privilegiada, su navegador ejecuta el script como si la aplicación misma lo hubiera escrito.

¿Por qué importa?

El JavaScript ejecutado corre en el contexto del dominio de la víctima: puede leer document.cookie (si no es HttpOnly), hacer peticiones en su nombre, capturar pulsaciones de teclado, redirigir a un sitio falso o modificar el contenido de la página. El XSS almacenado es el más peligroso porque no necesitas convencer a nadie de pulsar un enlace: basta con que visite la página.

Profundización

El escapado depende del contexto. No es lo mismo insertar datos dentro de texto HTML, dentro de un atributo entre comillas, dentro de un bloque <script> o dentro de una URL: cada contexto necesita una codificación distinta. Por eso "quitar <script>" nunca es una defensa completa: existen <img onerror>, <svg onload> y muchas otras etiquetas y eventos. Las cookies con HttpOnly impiden leerlas desde JavaScript, y una CSP con nonce o hash puede bloquear scripts inline aunque el HTML sea vulnerable.

Ejemplo de código vulnerable 
note_to_piglin = request.form.get("note_to_piglin", "")
# se guarda sin sanitizar y luego se muestra con |safe:
# <div>{{ note_to_piglin | safe }}</div>
Más ejemplos de script (no son la solución) 
<script>alert(1)</script>
<script>console.log('XSS')</script>
<img src=x onerror=alert(1)>
<svg onload=alert(1)>
<body onload=alert(1)>
<a href="javascript:alert(1)">haz clic</a>
<iframe src="javascript:alert(1)"></iframe>
Payload de referencia (ábrelo solo si te atascas) 
<script>fetch('/endpoint?cookie=' + encodeURIComponent(document.cookie));</script>

Observa qué información sale del navegador de la víctima y hacia dónde. En un entorno real, ese endpoint sería controlado por el atacante.

Cómo defenderse: escapar la salida según el contexto (nunca |safe con datos de usuario), validar la entrada, usar una Content Security Policy estricta, marcar cookies con HttpOnly, Secure y SameSite, y sanitizar HTML con una librería reconocida si se permite formato.
Al terminar, comprueba que puedes:
  • Diferenciar XSS reflejado, almacenado y DOM-based.
  • Explicar por qué |safe es peligroso aquí.
  • Nombrar dos medidas que reduzcan el impacto aunque exista XSS.
Curiosidad: en 2005 el gusano "Samy" se propagó por MySpace usando XSS almacenado: cada perfil visitado infectaba al visitante. En menos de una hora superó el millón de perfiles y MySpace tuvo que cerrar temporalmente la web.

5. Vara de Blaze

Unrestricted File Upload → RCE
{% if 'blaze' in inv %}✓ Resuelta{% endif %}
Dificultad: Media Nether Prerrequisito: tema 3 OWASP: A04 / RCE

Objetivo de aprendizaje: identificar qué validaciones faltan en un formulario de subida y entender cómo un archivo inocente se convierte en ejecución remota de código.

¿Qué es?

La subida de archivos irrestricta ocurre cuando el servidor acepta cualquier archivo, no comprueba su tipo real y además lo guarda en un lugar desde el que puede ser ejecutado. El resultado es una webshell: un script subido por el atacante que el servidor ejecuta con sus propios permisos.

¿Cómo funciona?

El formulario recibe el archivo, secure_filename() limpia el nombre (quita rutas y caracteres raros) pero no valida la extensión ni el contenido. Luego se guarda en una carpeta accesible y existe una forma de ejecutarlo. Un script de Python puede abrir archivos del servidor y devolver su contenido: eso ya es RCE (Remote Code Execution).

¿Por qué importa?

La ejecución remota de código es el escalation máximo en un servidor web: permite leer credenciales, moverse lateralmente, instalar persistencia o usar el equipo como plataforma de ataque. Un simple formulario de "sube tu avatar" mal validado ha sido el punto de entrada de numerosos incidentes reales.

Profundización

Validar solo por extensión es insuficiente: foto.png.php puede engañar a un filtro que mira solo el final, y el Content-Type lo envía el cliente, así que se puede falsificar. Lo robusto es comprobar los magic bytes del archivo (los primeros bytes que identifican el formato), usar una allowlist de extensiones, renombrar el archivo con un nombre aleatorio, guardarlo fuera del directorio web y asegurar que el servidor no tenga permiso de ejecución en la carpeta de subidas.

Ejemplo de código vulnerable 
filename = secure_filename(file.filename)
file.save(os.path.join(UPLOAD_FOLDER, filename))
# Sin allowlist de extensión, sin comprobación de magic bytes
# y con ruta de ejecución accesible para el usuario.
Comandos para crear la carpeta y el script desde la terminal 
# Crear un directorio de trabajo:
mkdir -p ~/ctf/blaze && cd ~/ctf/blaze

# Crear el script con un editor:
nano receta.py

# O generarlo con una línea:
echo "print(open('/ruta/del/archivo').read())" > receta.py

# Comprobar lo que has creado:
cat receta.py
ls -la
Pista conceptual (ábrela solo si te atascas)

Piensa en el contenido del script antes que en su nombre: ¿qué información quieres que el servidor te devuelva? Después observa qué extensión acepta el formulario y cómo se ofrece la ejecución. La extensión correcta es parte del rompecabezas.

Cómo defenderse: allowlist de extensiones y MIME, verificación de magic bytes, almacenamiento fuera del webroot, nombres aleatorios, permisos de solo lectura en la carpeta de subidas, desactivar la ejecución de scripts en esa ruta y escanear los archivos con antivirus.
Al terminar, comprueba que puedes:
  • Explicar por qué secure_filename() no basta.
  • Definir webshell y RCE con tus palabras.
  • Listar tres validaciones que debería tener el formulario.
Curiosidad: muchas webshells se han ocultado dentro de imágenes reales (unión de bytes válidos de PNG más código PHP/Python al final). Por eso mirar solo la extensión o el icono del archivo nunca es suficiente.

6. Ojo de Ender

Broken Access Control y parameter tampering
{% if 'pearl' in inv %}✓ Resuelta{% endif %}
Dificultad: Media Nether Prerrequisito: tema 3 OWASP: A01 Broken Access Control

Objetivo de aprendizaje: entender que el navegador es un cliente hostil y que ninguna decisión de seguridad puede tomarse en función de un dato que el propio cliente envía.

¿Qué es?

El control de acceso roto (Broken Access Control, A01 del OWASP Top 10) agrupa los fallos que permiten a un usuario hacer cosas para las que no está autorizado. El parameter tampering es una de sus formas: modificar parámetros, cookies o campos ocultos para engañar al servidor sobre tu identidad o tu rol.

¿Cómo funciona?

El servidor lee el rol desde un parámetro o una cookie (user_role) y decide qué permisos conceder. Como ese valor viaja en la petición, quien controla el navegador puede cambiarlo. El error no está en que el dato sea modificable —todos lo son—, sino en que el servidor lo acepte como prueba de identidad sin contrastarlo con la sesión real.

¿Por qué importa?

Es la puerta más directa a la escalada de privilegios: pasar de "visitante" a "administrador" con cambiar una cadena. Una variante muy común es el IDOR (Insecure Direct Object Reference): cambiar un identificador en la petición para ver el registro de otra persona. OWASP lo coloca en el puesto A01 precisamente por su frecuencia y su impacto.

Profundización

El flujo de carpetas en la terminal que aparece abajo no es decorativo: es la fase de reconocimiento local. Con pwd, ls, cd, find y cat descubres dónde están los artefactos del reto y qué nombres usan. Después aplicas el mismo criterio a la capa web: con Burp Suite interceptas la petición y observas qué campos viajan (rol, usuario, identificador). La habilidad transferible es la misma: descubrir qué datos controla el cliente y preguntarse si el servidor debería fiarse de ellos.

Ejemplo de código vulnerable 
user_role = request.args.get("user_role") or request.cookies.get("user_role", "guest_traveler")

if user_role in ["ender_master", "admin"]:
    grant_secret_access()  # se concede acceso sin verificar la sesión real
Flujo de carpetas en la terminal (reconocimiento) 
# ¿Dónde estoy?
pwd

# ¿Qué hay aquí?
ls -la

# Entrar y subir un nivel:
cd nombre_carpeta
cd ..

# Localizar y leer archivos:
find . -name "*.txt"
cat archivo.txt
Pista conceptual (ábrela solo si te atascas)

Con la terminal identifica los nombres que usa el sistema. Luego, en la petición web, fíjate en el campo que indica tu rol: el servidor confía en él más de lo que debería. No necesitas una contraseña; necesitas que el servidor pregunte a su propia sesión, no al cliente.

Cómo defenderse: decidir permisos siempre en el servidor a partir de la sesión autenticada; nunca confiar en parámetros, cookies ni campos ocultos; firmar o cifrar las cookies; aplicar RBAC con default deny y verificar la propiedad de cada objeto (defensa contra IDOR).
Al terminar, comprueba que puedes:
  • Explicar por qué "el cliente miente" es el punto de partida.
  • Definir IDOR y en qué se parece al parameter tampering.
  • Escribir la comprobación segura usando la sesión del servidor.
Curiosidad: durante años, numerosos paneles de administración consideraban "administrador" a quien enviaba un parámetro admin=true. La corrección no fue ocultar el parámetro, sino dejar de creer en él.

7. Cristales del End

Explotación de servicio y backdoor (CVE simulado)
{% if 'crystals' in inv %}✓ Resuelta{% endif %}
Dificultad: Media/Alta The End Prerrequisito: tema 6 Familia: exploit / supply chain

Objetivo de aprendizaje: reconocer el patrón de una puerta trasera por token fijo, entender cómo se activa y por qué ese diseño es tan frágil frente a cualquiera que lea el código.

¿Qué es?

Una backdoor o puerta trasera es código deliberadamente oculto en un sistema para permitir acceso no autorizado. Un CVE (Common Vulnerabilities and Exposures) es un identificador público para una vulnerabilidad conocida. Aquí se simula un servicio con una backdoor activable por una cadena concreta.

¿Cómo funciona?

El servicio recibe tu payload y lo compara con una lista de disparadores (triggers) escritos literalmente en el código. Si alguno aparece, ejecuta una orden interna que destruye los cristales. No hay autenticación, no hay firma criptográfica: solo una comparación de texto. Por eso basta con descubrir el token para activarla.

¿Por qué importa?

Las backdoors converting cualquier superficie de entrada en un interruptor de acceso total. Son especialmente graves cuando llegan por supply chain: el software legítimo que instalas ya contiene la puerta. El impacto típico es ejecución remota, persistencia y robo de información sin generar eventos de login normales.

Profundización

Esta backdoor usa un token fijo, lo que la hace muy detectable por quien lea el código fuente o compare hashes del binario con una versión confiable. En el mundo real hay backdoors más sutiles: se activan con una cabecera HTTP concreta, con un User-Agent extraño o con una secuencia de bytes en un protocolo. Por eso la defensa combina revisión de código, firma de artefactos, comparación de integridad, SBOM y monitorización de procesos hijos de servicios web. Fíjate también en la diferencia entre un trigger simple (token) y uno con concatenación (token;acción): el segundo aprovecha que la entrada acaba llegando a una shell, tema de la bandera 8.

Ejemplo de código vulnerable 
TRIGGERS = ["CVE-2026-OVERLOAD", "AB;", "shatter_crystals", "OVERLOAD_CRYSTALS"]

if any(trigger in payload for trigger in TRIGGERS):
    run_sandboxed("shatter_crystals")  # acceso sin autenticación
Más ejemplos de exploit (no son la solución) 
# Formas típicas de escribir un disparador:
CVE-2026-OVERLOAD
AB;
OVERLOAD_CRYSTALS
shatter_crystals

# Concatenación conceptual (prepara el tema de Command Injection):
valor; ls

8. Ender Dragón

Inyección de comandos (Command Injection)
{% if 'dragon' in inv %}✓ Resuelta{% endif %}
Dificultad: Alta The End Prerrequisito: tema 7 OWASP: A03 Injection

Objetivo de aprendizaje: entender cómo un dato del usuario se convierte en parte de una orden del sistema operativo y cómo usar metacaracteres para cambiar el comando que se ejecuta.

¿Qué es?

La inyección de comandos (OS Command Injection) ocurre cuando una aplicación pasa entrada del usuario a una shell del sistema operativo sin sanitizarla. La diferencia con SQLi es el intérprete: aquí no engañas a una base de datos, engañas a /bin/sh, cmd.exe o equivalente.

¿Cómo funciona?

El código construye una cadena con una f-string y la ejecuta con shell=True. La shell analiza esa cadena completa y no sabe qué parte era tu dato y cuál era la orden original. Los metacaracteres ;, &&, |, &, $( ), las comillas invertidas y el salto de línea tienen significado especial: permiten terminar el comando legítimo y añadir otro.

¿Por qué importa?

Es ejecución remota de código en su forma más directa: leer archivos, listar directorios, abrir una reverse shell, modificar configuración o moverse a otros equipos de la red. El proceso se ejecuta con los permisos del servicio web, así que el impacto depende de cómo esté configurado ese usuario.

Profundización

La raíz del problema es shell=True. Con subprocess.run(["echo", valor], shell=False), el valor se pasa como un único argumento y ningún metacarácter se interpreta: es la forma correcta. Cuando no queda más remedio que usar shell, hay que escapar con shlex.quote() y validar con una allowlist, pero seguirá siendo frágil. También existe la blind command injection: la aplicación no devuelve la salida, así que se confirma con retardos (sleep) o con peticiones salientes. El playground del reto muestra en tiempo real cómo se construye el comando y qué metacaracteres introduces: úsalo para observar, no solo para acertar.

Ejemplo de código vulnerable 
cmd = f"echo 'Calculando impacto de flecha: potencia {shot_power}'"
output, error = run_sandboxed(cmd, shell=True)
# shot_power llega sin validar y se interpreta como sintaxis de shell
Comandos de ejemplo (no son la solución) 
# Metacaracteres y qué hacen:
valor; comando      # ejecuta el segundo comando después del primero
valor && comando    # ejecuta el segundo solo si el primero funciona
valor | comando     # usa la salida del primero como entrada del segundo

# Forma segura en Python, para comparar:
subprocess.run(["echo", valor], shell=False)
Comando inicial de referencia (ábrelo solo si te atascas) 
100; cat /secret/dragon_slain.txt

# Variantes:
100 && cat /secret/dragon_slain.txt
100 | cat /secret/dragon_slain.txt

Fíjate en la estructura: un valor numérico válido, un separador y una orden de lectura. El número mantiene contento al validador superficial; el separador hace el trabajo real.

Cómo defenderse: evitar shell=True, usar APIs que acepten listas de argumentos, validar tipos y rangos (por aquí, numérico), aplicar allowlists, escapar con shlex.quote() si no hay alternativa y ejecutar el servicio con el mínimo privilegio posible.
Al terminar, comprueba que puedes:
  • Explicar la diferencia entre ; y &&.
  • Escribir la versión segura con shell=False.
  • Describir la command injection ciega y cómo se detecta.
Curiosidad: Shellshock (CVE-2014-6271) permitía ejecutar comandos arbitrarios mediante variables de entorno en Bash. Afectó a millones de servidores y dispositivos IoT: un simple encabezado HTTP bastaba para comprometerlos.

9. Huevo de Dragón

Enumeración de Active Directory con PowerView
{% if 'egg' in inv %}✓ Resuelta{% endif %}
Dificultad: Alta The End Prerrequisito: tema 6 Familia: AD / post-explotación

Objetivo de aprendizaje: comprender cómo se enumera un dominio de Active Directory para descubrir usuarios, grupos, equipos y recursos compartidos, y por qué esa información abre la puerta a siguientes fases del ataque.

¿Qué es?

Active Directory (AD) es el servicio de directorio de Windows que centraliza identidades: usuarios, grupos, equipos y políticas. PowerView, parte de la suite PowerSploit, es una herramienta de auditoría que consulta AD mediante LDAP y SMB para enumerar esos objetos. En este reto la consola es simulada: no ejecuta PowerShell real ni accede al sistema de archivos, solo resuelve los cmdlets contra un dominio ficticio.

¿Cómo funciona?

La enumeración sigue un orden lógico: primero identificar el dominio y sus controladores; después listar usuarios y grupos; luego equipos y recursos compartidos; y finalmente correlacionar pistas. Las descripciones de cuentas de servicio suelen contener notas internas con nombres de servidores o rutas: son oro para el atacante porque revelan dónde están los datos sin need de explotar nada.

¿Por qué importa?

En pentesting, la enumeración de AD es la fase que convierte un acceso inicial en un mapa completo del dominio. Permite encontrar cuentas privilegiadas, shares mal protegidos y rutas de movimiento lateral. Herramientas como BloodHound grafican esas relaciones y muestran el camino más corto hasta el objetivo.

Profundización

Cada cmdlet responde una pregunta distinta: Get-NetDomain identifica el dominio, Get-NetDomainController localiza los DC, Get-NetUser y Get-NetGroup mapean identidades, Get-NetGroupMember revela pertenencias, Get-NetComputer lista equipos, Get-NetShare y Find-DomainShare encuentran recursos compartidos, e Invoke-UserHunter busca dónde hay sesiones de usuarios. La defensa se apoya en mínimo privilegio sobre los shares, cuentas de servicio administradas (gMSA) para no guardar contraseñas en descripciones, y monitorización de consultas LDAP y eventos de acceso a SMB. Los atacantes, por su parte, suelen ocultar estas consultas tras procesos legítimos de PowerShell.

Pista conceptual (ábrela solo si te atascas)

No busques el archivo directamente. Primero lee las descripciones de los usuarios: alguna cuenta de servicio suele mencionar el recurso. Cuando sepas el equipo y el nombre del share, usa Get-NetShare y Find-DomainShare para confirmarlos.

Cómo defenderse: aplicar mínimo privilegio en shares, usar gMSA en lugar de contraseñas escritas en descripciones, no guardar rutas internas en campos de texto, monitorizar LDAP/SMB y eventos 4662/5140, restringir PowerShell conConstrained Language Mode y revisar periódicamente la pertenencia a grupos privilegiados.
Al terminar, comprueba que puedes:
  • Explicar para qué sirve cada familia de cmdlets listada.
  • Describir cómo una descripción de cuenta filtra información.
  • Nombrar dos medidas defensivas contra la enumeración de AD.
Curiosidad: PowerView forma parte de PowerSploit y se creó para auditorías legítimas de Active Directory. Irónicamente, su popularidad en auditorías es la misma que en ataques reales: la diferencia está en la autorización, no en las herramientas.

10. Método de Aprendizaje Recomendado

Un plan de estudio, no una lista de respuestas

Objetivo: convertir nueve retos en competencias reutilizables. El secreto no es acertar la flag, sino poder explicar luego qué fallaba y cómo se arregla.

Fase 0 · Prepara tu entorno

Ten a mano un navegador con herramientas de desarrollo, una terminal de Kali Linux (o similar) y un editor de texto. Crea una carpeta de trabajo por dimensión y lleva una bitácora: escribe qué observas, qué pruebas y qué resultado obtienes. La bitácora es lo que diferencia "copiar un payload" de "aprender".

Fase 1 · Overworld: observar antes de explotar

Con las banderas 1 a 3 practica el reconocimiento: metadatos, cadenas codificadas, consultas a bases de datos y enumeración de consolas. Repite el ciclo observar → hipotetizar → probar → explicar. Si no puedes explicar por qué funcionó, vuelve al apartado "Profundización" del tema.

Fase 2 · Nether: el navegador y el servidor

Con las banderas 4 a 6 cambia el foco a la web: código que se ejecuta en navegadores ajenos, archivos que el servidor no debería ejecutar y roles que el cliente no debería decidir. Aquí conviene usar las DevTools y Burp Suite para ver qué viaja realmente en cada petición.

Fase 3 · The End: servicios y dominios

Las banderas 7 a 9 elevan el nivel: backdoors, shells y enumeración de Active Directory. Antes de tocar nada, lee el código con el botón "Ver Código" y señala en voz alta la línea donde se confía ciegamente en la entrada. Después usa el playground del Dragón para ver el comando construido en tiempo real.

Hábitos que aceleran el aprendizaje

  • Usa "Ver Código": está pensado para que identifiques la línea vulnerable, no para copiar y pegar.
  • Compra pistas con XP: las pistas son conceptuales; piden dirección, no la respuesta.
  • Explica en voz alta: si no puedes explicar el ataque a un compañero, aún no lo dominas.
  • Cambia una variable: prueba otra extensión, otro separador, otro parámetro. Aprenderás más de los fallos que de los aciertos.
  • Escribe la defensa: por cada bandera, anota cómo la evitarías como desarrollador.
Checklist final antes de dar por terminado el laboratorio:
  • Puedo explicar los nueve temas sin mirar esta guía.
  • Sé nombrar una defensa concreta para cada uno.
  • He completado las tres dimensiones y entiendo por qué una desbloquea la siguiente.
  • He usado la guía como referencia, no como solucionario.
Curiosidad: en seguridad, la competencia más buscada no es memorizar payloads, sino saber qué preguntar cuando algo no funciona. Esta guía está diseñada para entrenar esa pregunta.

11. Glosario exprés

Términos que aparecen a lo largo de la guía
Allowlist
Lista de elementos permitidos; todo lo demás se rechaza por defecto.
Blocklist
Lista de elementos prohibidos; todo lo demás se permite. Más débil que una allowlist.
Blind injection
Inyección cuyo resultado no se muestra; se infiere por tiempo o por cambios de comportamiento.
CVE
Identificador público de una vulnerabilidad conocida, con formato CVE-AÑO-NÚMERO.
CSP
Content Security Policy: cabecera que limita qué scripts y recursos puede cargar el navegador.
HttpOnly
Atributo de cookie que impide leerla desde JavaScript, mitigando el robo por XSS.
IDOR
Referencia directa a objetos insegura: cambiar un identificador para acceder a datos ajenos.
Metacarácter
Carácter con significado especial para un intérprete, como ;, | o '.
Payload
Datos deliberadamente construidos para provocar un comportamiento concreto en el objetivo.
RCE
Remote Code Execution: ejecución de código en un sistema remoto.
Supply chain
Riesgo introducido a través de dependencias o software de terceros aparentemente legítimo.
XSS
Cross-Site Scripting: inyección de scripts en el navegador de otro usuario.
Recuerda: una herramienta no sustituye al criterio. Entiende el problema antes de elegir el comando.
